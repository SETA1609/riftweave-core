# M5-76 A development branch takes every merge, and main takes only development

Date: 2026-11-17

- **Decision:** pull requests merge into `development`; `main` takes only `development`, at a release. The workflows that commit after a merge push to `development`, which is not protected against them, so no token is needed. Owner, 2026-11-17, replacing the first fix in this issue (a push token).
- **Evidence** [V 2026-11-17]: the Actions API lists 83 runs and no success. `main` reports `protected: true`, enforced for non-admins. The close step ran 82 s, the length of five push attempts with waits of 5 to 25 s. `devops-tools close-merged-issue` run locally on `main` closed M5-69 correctly. The run logs need a login and were not read [U], so "the push is rejected" is an inference from the timing and the protection.
- **Rejected:** a push token (`ISSUE_CLOSER_TOKEN`) that may bypass the protection on `main`. It works, but it is a secret that can push past every rule. devops_tools Issue 12 (an optional `push-token`, and a quick failure when a push is rejected rather than raced) stays useful on its own and is not needed here; the pin is unchanged.
- **The release pull request** (`development` into `main`) names no issue, so the changelog check does not run on it, and the rebase does not touch it, because it rebases only pull requests that target `development`.
- **Risk:** a branch made from `main` instead of `development` misses merged work until the next release; the docs say to branch from `development`, and making it the default branch makes that the default.
- **Cleanup dates:** each `Merged:` date is the commit date of the squash commit on `main`.
