# M5-76 Close merged issues on the protected main branch

Date: 2026-11-17

- **Decision:** the closing commit is pushed with a token allowed past the protection (`ISSUE_CLOSER_TOKEN`, passed as devops_tools' new `push-token` secret), not by loosening the protection on `main`. Owner request, 2026-11-17, "fix the workflow".
- **Evidence** [V 2026-11-17]: the Actions API lists 83 runs and no success. `main` reports `protected: true`, enforced for non-admins. The close step ran 82 s, the length of five push attempts with waits of 5 to 25 s. `devops-tools close-merged-issue` run locally on `main` closed M5-69 correctly. The run logs need a login and were not read [U], so "the push is rejected" is an inference from the timing and the protection.
- **Why not a pull request per close:** a pull request opened with `GITHUB_TOKEN` starts no checks and needs a person to merge it, so issues would wait again.
- **Why a fine-grained token:** it can be limited to this repository and to Contents. A GitHub App token is the stronger choice if more repositories need it later. [A]
- **Pin:** all three workflows and `tools/devops/` point to `1fae926`, the commit on devops_tools' `issue-12-close-merged-issue-on-a-protected-branch`. Re-pin to its merge commit on devops_tools `main` before this merges, since a squash merge leaves the branch commit off `main`.
- **Risk:** the token can push to `main` past every protection, so it is stored only as an Actions secret and used only by this workflow; the reusable workflow runs a pinned commit.
- **Cleanup dates:** each `Merged:` date is the commit date of the squash commit on `main`.
