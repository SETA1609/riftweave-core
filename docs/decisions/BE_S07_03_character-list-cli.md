# BE_S07_03_character-list-cli A character list, and characters travel between players and the GM as files (backend)

Date: 2026-11-20

- **Decision:** the sync fields live in the file envelope, not in the stored actor: a character file gains `character` (`id`, `name`, `revision`, `changed_by`, `changed_at`, `common.json#/definitions/character`) beside `data`. The stored actor is the core's state and holds no name or bookkeeping, and `data` stays exactly what the contract returns (APP-30). `name` and `changed_at` are added to the issue's three keys because the list shows the name and the last change. [V 2026-11-20, `test_contract.py`, `go test ./cmd/riftweave`]
- **A file without sync fields still imports,** as a new character at revision 1, so APP-30's character files and the frontend's current export keep working until `FE_S07_04_character-list-page` writes the fields. [A]
- **The sync rule** is in docs/backend/files.md#the-sync-rule: a higher revision replaces, a lower one is refused with a note, the same revision with the same name and actor is unchanged, and with other content it diverges: both sides are shown and nothing changes until the person keeps one (`--keep saved|incoming` in the CLI, a second prompt in the TUI). Never field by field (owner, 2026-11-16). `changed_by` and `changed_at` are not content. [A]
- **The party is session data the core carries, not a rule:** `session.party[]` holds each member's sync fields as loaded (so the revision it started from), its actor as loaded (`start`), and its actor now. `start`, `step`, and `replay` carry it unchanged; no step touches a member yet. The GM's party export raises the revision and sets `changed_by: gm` only for a member whose actor changed. Changing members is `BE_S08_07_encounter-tracker-cli`'s; the tests stand in for it by editing the session file. [A]
- **The CLI list** is a directory of character files named by id, under the settings directory (`characters/`), so `RIFTWEAVE_CONFIG_DIR` moves both. The list is sorted by name, then id. [A]
- **The menu:** Characters is live in the CLI and still pending in the browser. `menu.json` gains `issue_apps`, the apps an entry's issue is pending in, so the entry names `FE_S07_04_character-list-page` with `issue_apps: ["web"]`. The frontend already dims any entry with an `issue`, so it needs no code change; its two specs expect the new id. [V 2026-11-20, Vitest and Playwright run locally]
- **Open:** whether a GM's library should also save the party's updated characters on export [U]; how the frontend shows a divergence (`FE_S07_04`); `frontend/src/api/openapi.d.ts` is behind the contract on `development` and is not regenerated here, since that would add unrelated changes. [U]
- **Risk:** two devices that both change a character without a hand-off end up with the same revision and other content, which is a divergence the person must settle; a GM who never exports the party leaves the players a revision behind. [A]
