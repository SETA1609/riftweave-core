#### DE_S04_01_base-perk-schema A base perk schema, and kinds that extend it
- Status: todo
- Priority: medium
- Needs: —
- Was: M5-58
- Modified: 2026-11-18
- Do: Owner request, 2026-11-15: `feature.schema.json` is one flat definition where every perk may carry every field (`modifiers`, `unlocks`, `summon_bonus`, `share`, `natural_weapon`), so nothing says which fields belong together. Split it into a base and kinds that extend it. **Base perk:** what every feature has (`key`, `label`, `description`, `source`, `type`, `category`, `prerequisite`, `ranks`, `modifiers`). **Kinds**, each the base plus its own fields: `stat` (modifiers only: Toughness, Alert), `grant` (`unlocks`: summon templates, bound-weapon materials), `summoning` (`summon_bonus`), `sharing` (`share`: the bard and skald perks), `natural_weapon` (`natural_weapon`: Catman Claws), and the next ones as they come. Data on main, 2026-11-15: 84 perks, 17 racial traits, and 10 creation traits carry modifiers only; 6 perks carry `unlocks`, 4 `share`, 2 `summon_bonus`, and one racial trait `natural_weapon`; no row carries two of these fields. [V 2026-11-15] Data-level inheritance (a perk row built on another) is M5-59, which builds on this issue.
- Decisions (owner, 2026-11-16: "your picks"):
  - **Draft-07 stays.** The base's properties are one shared definition (`basePerkProperties`); each kind lists them plus its own fields, with its own `additionalProperties: false`. No move to 2019-09 or 2020-12. [A]
  - **An explicit `kind` field**, and `if`/`then` on it picks the kind's fields, so an error names the kind ("a `sharing` perk may not have `unlocks`") instead of the noise of a `oneOf` over shapes.
  - **The name is `kind`.** `CONTRIBUTING.md#naming` says the difference: `type` is how a feature is gained (perk, creation, racial_trait, universal), `kind` is what it does.
  - **One kind per row.** No row combines two today; a perk that needs two is split into two perks until content shows a combined need. [A]
  - **Every feature type takes a kind**, not only perks: Catman Claws (a racial trait) is a `natural_weapon` row like any perk that grants claws.
  - **`modifiers` is optional for `grant`, `summoning`, and `sharing`**, and stays required for `stat` and a row with no kind. The filler bonuses that rule forced (the +5 skill on the summoning perks) may be removed in this issue, each listed in the decision record.
  - **Modules use the core kinds now.** A module's own kind (a module schema built on the core base, loaded from the manifest's `schemas`) is later work, filed when a module needs one.
  - **Go keeps one `Feature` struct** with optional fields and gains `Kind`; no typed kind per struct.
  - **No `kind` means the base kind** (modifiers only). Each row with a specialised field gets its `kind` here; a module whose perks use only base fields needs no change, so this is not breaking.
  - **Shapes in the schema, cross-row checks in `validate.py`.** Which fields a kind has is schema; refs resolving and the share rank against `rank_share` stay in the validator.
  - **The data model diagram** (M5-57) draws each kind as its own box under FEATURES, with its own references.
  - **Perks only.** The same pattern may fit spells (M3-26) and monsters later; the decision record names it as the pattern to follow.
- Keys: `basePerkProperties`; `kind` on features (`stat`, `grant`, `summoning`, `sharing`, `natural_weapon`)
