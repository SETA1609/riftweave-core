#### M5-62 One project version, and a release that tags it
- Status: todo
- Priority: high
- Needs: —
- Modified: 2026-11-16
- Do: Owner request, 2026-11-16: track the project's version so releases are tags, and a tag deploys the frontend (APP-15). The policy exists (`docs/core/versioning.md`, M5-07: semver, what is breaking, `key_diff.py`), but nothing holds the version and no tag exists. Today the version is scattered: `frontend/package.json` says `0.0.0`, `backend/core/author.go` writes `0.1.0` into an exported manifest, and APP-16 adds `core.RulesVersion` `0.1.0`. **One source:** a `VERSION` file at the repo root (`0.1.0` at first) [A]. The Go core reads it at build time without leaving its module (a copy embedded by `go generate`, or `-ldflags` from the build scripts, picked in the decision record [A]) and a test fails when the two differ; `frontend/package.json` `version` and the author manifest's `version` come from it, checked by the same test. **Release, its own PR** (`changes/README.md#releasing`): on a branch from `main`, `devops-tools changelog-fragments release --section-title "v<version>"` moves the fragments into `CHANGELOG.md`, `VERSION` moves (MINOR before 1.0, as the roadmap's table says), and `key_diff.py <last tag> WORKTREE` runs: every removed key needs a **Removed (breaking)** bullet. **The tag:** once that PR merges, the owner tags the merge commit `v<version>`. A workflow `.github/workflows/release.yml` on `v*` tags checks that the tag equals `VERSION`, that `CHANGELOG.md` has its section, and that the key diff from the previous tag is covered, then creates the GitHub release with that section as its notes; `pages.yml` (APP-15) publishes the app on the same tag. Pin every action by commit; a release step reads the tag only through `env:`. Write the steps in `CONTRIBUTING.md#releasing` and link them from the roadmap's "Versions and releases".
