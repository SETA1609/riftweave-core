#### M5-58 A base perk schema, and kinds that extend it
- Status: todo
- Priority: low
- Needs: M3-14
- Modified: 2026-11-15
- Do: Owner request, 2026-11-15: `feature.schema.json` is one flat definition where every perk may carry every field (`modifiers`, `unlocks`, `summon_bonus`, `share`, `natural_weapon`), so nothing says which fields belong together. Split it into a base and kinds that extend it. **Base perk:** what every feature has (`key`, `label`, `description`, `source`, `type`, `category`, `prerequisite`, `ranks`, `modifiers`). **Kinds**, each the base plus its own fields: a stat perk (modifiers only: Toughness, Alert), a grant perk that unlocks something (`unlocks`: summon templates, bound-weapon materials), a summoning perk (`summon_bonus`), a sharing perk (`share`: the bard and skald perks), a natural-weapon perk (`natural_weapon`), and the next ones as they come. A row names its kind, so the validator checks it against that kind's fields and refuses a field from another kind [A]; a row with no kind is a base perk. Module perks (`docs/modules/module-system.md`) refer to the same definitions, so a module's perk is a core kind or a module's own kind built on the base. Draft-07, which `validate.py` uses, has no `unevaluatedProperties`, so a base with `additionalProperties: false` cannot be extended by `allOf`. Either move the schemas to draft 2019-09 or later, or keep the base's properties as a shared definition that each kind lists with its own `additionalProperties: false`, and pick one in the decision record [A]. The same pattern may later fit spells (M3-26 already has a base spell) and monsters; this issue does perks only.
- Keys: the base perk definition; a `kind` on perks (or `oneOf` the kinds) [A]
