#### M5-77 Issue id prefixes that say what an issue is about
- Status: todo
- Priority: medium
- Needs: M5-76
- Modified: 2026-11-17
- Do: Owner request, 2026-11-17: track issue ids better. Add a table that says what each prefix means, and decide whether `APP` becomes `B` (backend) and `F` (frontend) and what `M5` stands for.
  - **Today** [V 2026-11-17, `docs/stories/README.md` and the issue files on `main`]: `M1` to `M6` are milestones in order (M1 kernel, M2 characters, M3 combat and magic, M4 world, M5 release 1.0, M6 content parity after 1.0). `APP` and `POST` are tracks, not milestones: `APP` is the reference backend, which holds the Go core, the command contract, both CLIs, the HTTP API, MCP, WebAssembly, and the Angular frontend; `POST` is the optional modules after 1.0. `SET` and `RW` are frozen ids of older trackers. Of 41 APP issues, most open ones change both `backend/` and `frontend/`.
  - **The problem:** a milestone number says nothing about the topic, and M5 ("Release 1.0, plus repo process and tooling") has become a catch-all. Of its open issues, only a few are release gates (M5-09 licensing and the tag, M5-18 the alpha playtest, M5-19 and M5-50 balance); the rest are tooling and process (M5-52, M5-53, M5-62, M5-76, this issue), diagrams (M5-63 to M5-66), perk and build content (M5-47, M5-58 to M5-61, M5-67), and data integrity (M5-40, M5-70 to M5-75).
  - **Proposal** [A, owner to confirm or change]:

    | Prefix | Means | Takes over |
    | --- | --- | --- |
    | `M1` to `M6` | Milestones only: the rules and content a release needs | M5 keeps its release gates and the 1.0 content |
    | `B` | Backend: Go core, command contract, agent and human CLIs, HTTP API, MCP, WebAssembly | APP issues that change only `backend/` |
    | `F` | Frontend: the Angular app | APP issues that change only `frontend/` |
    | `T` | Tooling and process: CI, workflows, formatting, versioning, diagrams, the tracker | M5 tooling, process, and diagram issues |
    | `D` | Data integrity: normal forms, naming, casing, one word per concept | M5-40, M5-70 to M5-75 |
    | `POST` | Optional modules after 1.0 | unchanged |
    | `APP`, `SET`, `RW` | Frozen: done issues keep them | nothing new |

  - **Full-stack APP issues** (rooms, settings, the character list, printing, and most others) split into a `B` issue and an `F` issue, the `F` one needing the `B` one, as the 20-file rule already splits ruleset and backend work. One is filed for each side, with its own branch, fragment, and decision file.
  - **Renumbering:** done issues keep their ids, as `SET` and `RW` did. Each open issue gets its new id, its file moves, and it carries `Was: <old id>`; every `Needs:` and link to it follows. `docs/stories/README.md` gets the prefix table and a full old-to-new table, so an old id in a changelog, decision, or commit message still resolves. An issue with an open branch (M5-47 today) is renamed only after it merges.
  - **Stories:** `B` and `F` replace `07-backend.md` with two story files, `T` and `D` get one each, and ROADMAP lists them as tracks beside `POST`.
  - **Tooling:** `roadmap-order` and `changelog-fragments` read ids with `issue-id-pattern` (`[A-Za-z][A-Za-z0-9]*...-[0-9]+`), which accepts one-letter prefixes; check that `roadmap-order` takes a story from the new files and that a branch named `B-01-...` finds its issue.
  - **Questions for the owner:** keep `M5` for 1.0 content (perks and builds), or move it to `M3` or `M6`? Do diagrams belong to `T` or to `D`? Is a one-letter prefix clear enough, or should it be `BE` and `FE`?
