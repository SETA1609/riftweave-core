#### M3-26 Spells compose from a base spell
- Status: todo
- Priority: medium
- Needs: —
- Do: Owner request, 2026-11-14: a spell can build on another spell and keep its qualities, as a monster builds on a creature type and a weapon on a base (docs/core/composition.md). A spell row may name `base` (a `core:spell/<key>` ref, or a module's) and `overrides` holding only the fields that differ. It resolves through the one `compose_row`, with no procedure of its own: start from the base spell, apply the overrides, and take identity (`key`, `label`, `source`) from the row itself. A base is a plain spell row and stays castable, unlike an equipment base with `is_item: false` [A]. A base may not itself name a base, so there is one level and no cycle [A]. A nested block such as M3-25's `summon` block merges per field, as `attributes` does today, so an override that writes `summon.count` keeps the base's `group` and `duration`; the merge table in composition.md gains that row. Python (`validate.py`) and the Go loader (`backend/internal/data/`) resolve spell bases before any check or command reads a spell, so every consumer reads the flat row. A GM's or a module's custom spell can build on a core one the same way. M3-25's minion spells are the first rows to use it.
- Keys: `base` and `overrides` on spell rows; a per-field merge for nested blocks

- See: docs/core/composition.md, ruleset/scripts/validate.py (`compose_row`, `_resolve_monster_bases`), backend/internal/data/data.go (monster and equipment bases)
- Done when: a spell row with `base` and `overrides` resolves to the base's fields plus the overrides in Python and Go; an override of one field in a nested block keeps the block's other fields; a base that does not resolve, or a base that names a base, fails validation; a casting vector casts a composed spell; `validate.py` and the tests pass.
