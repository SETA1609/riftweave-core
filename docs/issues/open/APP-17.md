#### APP-17 Rooms: a GM and up to four players share one session log
- Status: todo
- Priority: low
- Needs: APP-15, APP-16
- Do: Owner request, 2026-11-14: a light virtual table, a GM and up to four players (five in all) in one room. No message broker: the shared state is one ordered log of session steps, and every browser runs the same WebAssembly core (APP-14) and replays it, so the server computes no rule. A small Supabase project holds it [A]: `rooms` (code, GM, rules version), `room_members` (at most five), and `room_steps` (`room_id`, `seq`, `author`, `step`, unique on `room_id` and `seq`). The order is the queue: a Postgres function `append_step(room, expected_seq, step)` inserts at the next `seq` in one transaction, and a client whose `expected_seq` is stale reads the new steps and resends. The same function rolls the dice the step needs (Postgres, not the client) and writes them into the step's input, so no one fakes a roll and a replay still reproduces it. Supabase Realtime pushes each new step to the room; a client joining late, or reconnecting, reads the log and replays it. Players join with a room code and Supabase anonymous sign-in, no account; row-level security limits reads and writes to members. Turn-based only: the CLI and the frontend have no real-time mode, so a room never needs one. Rooms are optional: with no room the app plays alone, offline, with its browser saves (APP-16). Check the free tier's limits (projects pause after inactivity, connection and message caps) against a five-person room and write them in the docs [U].
